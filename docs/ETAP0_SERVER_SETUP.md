## 0. Общая картина: что мы делаем и зачем

Представь, что VPS — это **пустой склад**, который ты арендуешь.
Сейчас на складе валяется чужой хлам (старые файлы). Наша задача:

| Шаг | Аналогия со складом | Что делаем технически |
|---|---|---|
| 1. Подключение | Получить ключи от склада и зайти внутрь | Подключиться по SSH |
| 2. Очистка | Вынести весь мусор, подмести | Удалить старые контейнеры, файлы, почистить диск |
| 3. Оборудование | Поставить стеллажи, свет, сигнализацию | Установить Docker, Git, файрвол UFW |
| 4. Товар | Завезти свой товар по полкам | Склонировать проект в `/opt/crm`, настроить `.env` |
| 5. Открытие | Повесить вывеску, открыть двери | Запустить `docker compose up`, настроить Nginx + SSL |

### Что ставится и зачем (каждый компонент — одним абзацем)

1. **Ubuntu** — операционная система сервера. Уже стоит у тебя на VPS
   (spaceweb.ru). Это как Windows, но для серверов: без картинок,
   только текст (терминал). Все команды ниже — для Ubuntu.
2. **SSH** — способ зайти на сервер с домашнего компьютера.
   Это как удалённый рабочий стол, но текстовый. Ты вводишь команды
   дома — они выполняются на сервере в дата-центре.
3. **Docker** — «контейнеры». Представь, что вместо установки программ
   прямо в систему мы кладём каждую программу в прозрачный sealed-box
   (контейнер) со всем необходимым внутри. Три box'а:
   `app` (наш сайт на Python), `db` (база PostgreSQL), `nginx` (привратник).
   Плюс: ничего не конфликтует, перенос на другой сервер — одной командой.
4. **Docker Compose** — «пульт», который запускает все три контейнера
   разом по файлу `docker-compose.yml`. Одна команда `docker compose up` —
   и весь CRM работает.
5. **Git** — система контроля версий + способ доставить код на сервер.
   Ты хранишь код на GitHub, а на сервере делаешь `git clone` (скачать)
   и потом `git pull` (обновить). Это как «скачать папку», но умное:
   докачивает только изменения.
6. **Nginx** — «привратник/администратор на ресепшене». Принимает всех
   посетителей сайта (порт 80/443), быстрые запросы (картинки, CSS)
   отдаёт сам, а сложные передаёт внутрь — Python-приложению.
7. **UFW (файрвол)** — «охранник с списком». Разрешает вход только
   через двери 22 (SSH), 80 (HTTP), 443 (HTTPS). Всё остальное закрыто.
8. **PostgreSQL** — база данных. Это «картотека», где лежат все лиды,
   контакты, пользователи. Живёт в своём контейнере, данные хранятся
   в volume `pgdata` (переживают перезапуск).
9. **SSL / Let's Encrypt** — «замочек» в браузере (https://).
   Шифрует трафик, чтобы пароли нельзя было подсмотреть. У тебя
   сертификат уже есть — мы его просто подключим к Nginx.
10. **`.env`-файл** — листок с паролями, который лежит ТОЛЬКО на сервере
    и никогда не попадает в Git. Там пароль от базы и секретный ключ.

### Что понадобится перед началом

- [ ] IP-адрес сервера (вида `185.123.45.67`) — в панели spaceweb.ru
- [ ] Пользователь (обычно `root`) и пароль от него — тоже в панели хостинга
- [ ] Домен (если есть), направленный на IP сервера (A-запись)
- [ ] Домашний компьютер с интернетом (Windows / macOS / Linux — подойдёт любой)
- [ ] ~1 час времени, никуда не торопиться

## ШАГ 1 — Как подключиться к серверу

### 1.1. Что такое терминал (30 секунд теории)

Терминал — это окно, куда ты печатаешь команды текстом.
Нет кнопок и мышки — только клавиатура. Это нормально:
серверами управляют именно так.

- **Windows 10/11:** нажми `Win + R`, напечатай `powershell`, нажми Enter.
  В открывшемся синем окне можно вводить команды. (Альтернатива: программа PuTTY.)
- **macOS:** Программы → Утилиты → Терминал.
- **Linux:** `Ctrl + Alt + T`.

### 1.2. Команда подключения

**Что делает:** открывает защищённое соединение с сервером.
**Зачем:** без этого ты не можешь ничего делать на VPS.

Введи в терминале (замени `185.123.45.67` на свой IP):

```bash
ssh root@185.123.45.67
```

Нажми Enter.

**Что должно появиться (первый раз):**

```
The authenticity of host '185.123.45.67' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxx.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Это сервер спрашивает: «ты точно хочешь подключиться к этому компьютеру?»
Напечатай `yes` и нажми Enter.

**Дальше появится:**

```
root@185.123.45.67's password:
```

Введи пароль от сервера (символы НЕ будут отображаться — это защита,
так и должно быть, просто печатай вслепую) и нажми Enter.

**Успех выглядит так** — приглашение изменилось:

```
root@ubuntu:~#
```

Строка `root@ubuntu:~#` означает: «ты внутри сервера, я готов к командам».
Всё, что ты введёшь дальше, выполняется НА СЕРВЕРЕ, а не дома.

### 1.3. Возможные ошибки шага 1

| Ошибка | Причина | Решение |
|---|---|---|
| `ssh: command not found` (старый Windows) | Нет SSH-клиента | Установи PuTTY с putty.org, или обнови Windows 10/11 |
| `Connection timed out` | Неверный IP, сервер выключен, блокирует провайдер | Проверь IP в панели spaceweb, проверь что VPS запущен |
| `Permission denied (password)` | Неверный пароль | Внимательно введи заново; сбрось пароль в панели хостинга |
| `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED` | IP переиспользован после переустановки сервера | Дома выполни `ssh-keygen -R 185.123.45.67`, потом подключись заново |
| Зависло после ввода пароля | Медленная сеть | Подожди 30 секунд; если висит — закрой окно и подключись снова |

### 1.4. Проверка: убедись, что ты на сервере

**Что делает:** показывает версию системы.
**Зачем:** убедиться, что команды идут на сервер и это Ubuntu.

```bash
cat /etc/os-release && free -h && df -h /
```

**Ожидаемый результат** — примерно такое:

```
NAME="Ubuntu"
VERSION="22.04.5 LTS (Jammy Jellyfish)"
...
Mem:           1.9Gi        ...
/dev/vda1       15G   ...   ...
```

Видишь `Ubuntu` и ~2 ГБ памяти и ~15 ГБ диска — всё сходится с твоим тарифом.

> Дальше все команды выполняются НА СЕРВЕРЕ (в том же окне `root@...`).
> Отдельно будет сказано, когда что-то надо делать дома.

## ШАГ 2 — Чистый сервер: переустановка ОС (рекомендуется) или очистка

### Вариант Б (рекомендуемый): переустановить ОС в панели хостинга

Вместо ручной чистки проще снести всё и поставить свежую систему.
Это как не отмывать старую квартиру, а въехать в новостройку:
быстрее, чище, никаких сюрпризов от прошлых жильцов.

> ✅ **Выбрано для проекта: Ubuntu 24.04 LTS.**
> Наш `setup.sh` поддерживает 20.04 / 22.04 / 24.04, так что всё ниже работает без изменений.

**Какую ОС выбрать:** **Ubuntu 22.04 LTS (64-bit)** — оптимальный выбор:
поддержка до 2027 года, Docker и все наши скрипты проверены именно на ней.
Если в панели есть только **Ubuntu 24.04 LTS** — бери её, тоже подойдёт
(наш `setup.sh` работает на 20.04 / 22.04 / 24.04).
НЕ бери: версии без метки LTS (например 23.10, 24.10), Debian/CentOS
и образы «с панелью ISPmanager» (панель съест память и займёт порты 80/443 —
нам нужна **чистая ОС без панели**).

**Как переустановить (панель spaceweb.ru):**

1. Зайди в панель управления spaceweb.ru.
2. Открой раздел **«Виртуальные серверы»**, выдели свой VPS.
3. Нажми **«Переустановить»** (переустановка ОС текущей услуги).
4. Выбери образ **Ubuntu 22.04 LTS без ISPmanager**, задай пароль root
   (запиши его! он понадобится для SSH).
5. Подтверди и **подожди 10–40 минут**, пока система ставится.

> ⚠️ **Переустановка стирает ВСЁ на сервере.** Убедись, что там нет ничего
> нужного (у нас там только мусор — так что всё в порядке).

**После переустановки:**

1. Дома выполни (замени IP на свой) — это сброс старого «отпечатка» сервера,
   иначе SSH будет ругаться `REMOTE HOST IDENTIFICATION HAS CHANGED`:
   ```bash
   ssh-keygen -R 185.123.45.67
   ```
2. Подключись заново как в шаге 1: `ssh root@185.123.45.67`.
3. **Шаг 2 (очистка) пропускается целиком** — переходи сразу к шагу 3.

### Вариант А: ручная очистка (если переустановку делать не хочешь)

### 2.1. Посмотри, что сейчас на сервере (безопасно)

**Что делает:** показывает занятое место и старые контейнеры.
**Зачем:** понять масштаб мусора перед уборкой.

```bash
df -h / && echo "---" && docker ps -a 2>/dev/null || echo "(docker нет или пуст)"
```

**Ожидаемый результат:** таблица диска + либо список контейнеров,
либо строка `(docker нет или пуст)`.

Ещё посмотри крупные папки:

```bash
du -sh /* 2>/dev/null | sort -rh | head -10
```

**Что должно появиться:** список вида `/var 2.1G`, `/usr 1.5G` и т.д.
Если какая-то левая папка (например `/old_site`) весит гигабайты — это и есть мусор.

### 2.2. Автоматическая очистка скриптом

В проекте есть готовый скрипт `scripts/clean_server.sh`.
Но проект ещё не склонирован на сервер, поэтому сначала скачаем
только этот скрипт напрямую с GitHub.

**Что делает команда 1:** скачивает скрипт очистки.
**Зачем:** не надо копировать текст вручную.

```bash
curl -fsSL -o /tmp/clean_server.sh https://raw.githubusercontent.com/Roses1s/detroid/arena/01a0c8d0-detroid/scripts/clean_server.sh && echo OK
```

**Ожидаемый результат:** слово `OK`.

> Если URL не сработает (ветка переименована) — открой файл
> `scripts/clean_server.sh` в репозитории через браузер и скопируй
> его содержимое в файл на сервере вручную через `nano` (см. ниже).

**Что делает команда 2:** запускает очистку.
**Зачем:** останавливает и удаляет все контейнеры/образы, чистит кэш.

```bash
sudo bash /tmp/clean_server.sh
```

Скрипт спросит подтверждение:

```
Удалить ВСЕ docker-контейнеры/образы/volume'ы и очистить мусор? [y/N]
```

Напечатай `y` и Enter — **только если уверен, что на сервере нет ничего нужного!**

**Ожидаемый результат** в конце:

```
Готово. Сервер чист.
```

### 2.3. Проверка после очистки

```bash
df -h / && docker ps -a 2>/dev/null; echo "код: $?"
```

**Ожидаемый результат:** свободного места стало заметно больше,
`docker ps -a` показывает пустоту (или «command not found» — это тоже нормально,
значит Docker вообще не стоял).

### 2.4. Возможные ошибки шага 2

| Ошибка | Причина | Решение |
|---|---|---|
| `curl: command not found` | Нет curl | Выполни `apt-get update && apt-get install -y curl` и повтори |
| `404 Not Found` от curl | Неверная ветка/URL | Скачай файл вручную: открой GitHub в браузере, скопируй текст, на сервере `nano /tmp/clean_server.sh`, вставь, `Ctrl+O`, Enter, `Ctrl+X` |

## ШАГ 3 — Установка всего необходимого

### 3.1. Запуск скрипта настройки

**Что делает:** обновляет Ubuntu, ставит Docker, Docker Compose,
Git, файрвол UFW, создаёт папку `/opt/crm`.
**Зачем:** один скрипт вместо 20 ручных команд.

Скачай и запусти (две команды):

```bash
curl -fsSL -o /tmp/setup.sh https://raw.githubusercontent.com/Roses1s/detroid/arena/01a0c8d0-detroid/scripts/setup.sh && echo OK
```

**Ожидаемый результат:** `OK`.

```bash
sudo bash /tmp/setup.sh
```

Теперь **подожди 5–15 минут**. На экране будет бежать много текста —
так и должно быть: скачиваются пакеты. Не закрывай окно!

**Успешный финал выглядит так:**

```
Готово! Дальше: настрой .env и запусти docker compose up (см. docs/ETAP0_SERVER_SETUP.md).
```

### 3.2. Что скрипт сделал под капотом (читать, не выполнять)

Для понимания, по порядку:

1. `apt-get update && apt-get upgrade -y` — обновил список программ
   и поставил свежие версии (как «обновления Windows»).
2. `apt-get install -y ca-certificates curl gnupg git ufw` —
   поставил базовые инструменты, включая Git и файрвол.
3. Добавил официальный репозиторий Docker и поставил
   `docker-ce`, `docker-compose-plugin` — сам Docker и пульт Compose.
4. `systemctl enable docker && systemctl start docker` — включил
   автозапуск Docker при перезагрузке сервера.
5. Настроил UFW: разрешил порты 22 (SSH), 80 (HTTP), 443 (HTTPS),
   всё остальное запретил. Это защита от сканеров интернета.
6. Создал папку `/opt/crm` — дом нашего проекта.

### 3.3. Проверка установок (обязательно!)

**Что делает:** показывает версии только что поставленных программ.
**Зачем:** убедиться, что установка прошла, а не «вроде бы».

Введи три команды по очереди:

```bash
docker --version
```

**Ожидаемый результат:** `Docker version 26.x.x, build ...`
(номер версии может отличаться — главное, что команда отвечает).

```bash
docker compose version
```

**Ожидаемый результат:** `Docker Compose version v2.x.x`

> Внимание: именно `docker compose` (через пробел, без дефиса).
> Старый `docker-compose` (с дефисом) нам не нужен.

```bash
git --version && ufw status
```

**Ожидаемый результат:**

```
git version 2.x.x
Status: active
...
22/tcp    ALLOW ...
80/tcp    ALLOW ...
443/tcp   ALLOW ...
```

Если `Status: active` и три порта разрешены — файрвол настроен правильно.

### 3.4. Возможные ошибки шага 3

| Ошибка | Причина | Решение |
|---|---|---|
| `E: Unable to locate package docker-ce` | Не добавился репозиторий (старая Ubuntu / нет интернета) | Проверь интернет: `ping -c 3 8.8.8.8`; проверь версию: `cat /etc/os-release` (нужна Ubuntu 20.04+); запусти скрипт ещё раз |
| `docker: permission denied` | Ты не root, а обычный пользователь | Добавляй `sudo` перед командами docker, либо выполни `sudo usermod -aG docker $USER` и переподключись |
| `ufw ... ERROR` | UFW конфликтует с панелью хостинга | Спроси поддержку spaceweb, есть ли свой файрвол; наш UFW можно оставить выключенным, если панель уже фильтрует порты |
| Скрипт оборвался на середине | Пропал интернет / кончилось место | Проверь `df -h /` (нужно минимум 2 ГБ свободно) и запусти скрипт заново — он безопасно продолжит |

## ШАГ 4 — Проект на сервере: папки, код, пароли

### 4.1. Клонирование репозитория

**Что делает:** скачивает код CRM с GitHub в папку `/opt/crm`.
**Зачем:** код должен физически лежать на сервере, чтобы Docker его запустил.

```bash
cd /opt/crm && git clone -b arena/01a0c8d0-detroid https://github.com/Roses1s/detroid.git .
```

Разбор команды по частям:

- `cd /opt/crm` — зайти в папку проекта (дом склада);
- `git clone` — «скачай репозиторий»;
- `-b arena/01a0c8d0-detroid` — нужная ветка (полка на складе GitHub);
- `https://github.com/Roses1s/detroid.git` — адрес репозитория;
- `.` (точка в конце) — «клонируй прямо сюда, а не в подпапку».

**Ожидаемый результат:**

```
Cloning into '.'...
...
done.
```

Проверь, что файлы на месте:

```bash
ls -la /opt/crm
```

**Ожидаемый результат:** список файлов, среди которых обязательно есть
`docker-compose.yml`, `wsgi.py`, папки `app`, `nginx`, `scripts`, `docs`.

> Если репозиторий приватный и GitHub спросит логин/пароль:
> пароль от аккаунта НЕ подойдёт — нужен Personal Access Token.
> Проще: в панели GitHub сделай репозиторий публичным на время настройки,
> либо добавь серверный SSH-ключ в Deploy keys. Самый простой путь для новичка —
> публичный репозиторий + сильные пароли в `.env` (он в Git не попадает).

### 4.2. Настройка `.env` — файла с паролями (автоматически)

**Вариант А — автоматический (рекомендуется): одна команда.**

```bash
curl -fsSL -o /tmp/gen_env.sh https://raw.githubusercontent.com/Roses1s/detroid/arena/01a0c8d0-detroid/scripts/gen_env.sh && sudo bash /tmp/gen_env.sh /opt/crm
```

**Что делает:** скачивает скрипт `gen_env.sh`, который сам создаёт `.env`,
генерирует случайный `SECRET_KEY` (64 символа) и пароль базы (20 символов),
записывает их в нужные места. Ручками ничего править не надо.

**Ожидаемый результат:**

```
═══════════════════════════════════════════════════
 .env настроен автоматически ✅
═══════════════════════════════════════════════════
 SECRET_KEY:        сгенерирован (64 символа)
 Пароль базы:       uRGjhxO1fzGR4RmyxwXb
═══════════════════════════════════════════════════
 ⚠️  СОХРАНИ ПАРОЛЬ БАЗЫ в надёжное место ...
```

**⚠️ Сохрани показанный пароль базы** в менеджер паролей или блокнот.
Если `.env` уже существовал — скрипт сохранит его копию в `.env.bak.*`.

**Вариант Б — вручную (запасной, если скрипт не сработал):**

```bash
cd /opt/crm && cp .env.example .env && ls -la .env
```

**Ожидаемый результат:** строка вида `-rw-r--r-- 1 root root ... .env` —
файл создан.

Теперь **обязательно** поменяй два значения: `SECRET_KEY` и `POSTGRES_PASSWORD`.
Открой файл в редакторе `nano` (простой, управляется клавиатурой):

```bash
nano /opt/crm/.env
```

Перед тобой откроется текст файла. Стрелками перейди к строкам:

```
SECRET_KEY=change-me-in-production-please-0123456789abcdef
...
POSTGRES_PASSWORD=crm_password_change_me
```

Сгенерируй секретный ключ **в другом окне терминала** (не закрывая nano,
открой второе подключение по SSH) командой:

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

**Ожидаемый результат:** длинная строка вида `a3f9c1...` (64 символа).
Скопируй её и вставь в nano вместо `change-me...`.

Пароль базы придумай сам: минимум 16 символов, буквы+цифры, например
`KrM9xQ2vL8nZ4pW7s`. Замени `crm_password_change_me` на него
(внимание: пароль встречается в файле ДВА раза — в `DATABASE_URL`
и в `POSTGRES_PASSWORD` — замени ОБА одинаково!).

Сохрани файл: нажми `Ctrl + O` (буква O), потом Enter, потом `Ctrl + X` (выход).

Проверь, что файл на месте и Git его игнорирует:

```bash
cd /opt/crm && git status --short | head -5; echo "---"; git check-ignore .env && echo ".env в Git НЕ попадёт (правильно)"
```

**Ожидаемый результат:** строка `.env` и `.env в Git НЕ попадёт (правильно)`.

### 4.3. Возможные ошибки шага 4

| Ошибка | Причина | Решение |
|---|---|---|
| `fatal: destination path '.' already exists and is not an empty directory` | В `/opt/crm` уже что-то лежит | Проверь `ls -la /opt/crm`; если там мусор — удали (`rm -rf /opt/crm/*`), если там уже проект — вместо clone выполни `git pull` |
| `Could not resolve host: github.com` | Нет интернета / DNS | `ping -c 3 8.8.8.8` — если пинга нет, перезагрузи сервер из панели хостинга и попробуй снова |
| `nano: command not found` | Нет редактора | `apt-get install -y nano` |
| Потерялся в nano | Незнакомые горячие клавиши | `Ctrl+O`, Enter — сохранить; `Ctrl+X` — выйти; `Ctrl+K` — вырезать строку |

## ШАГ 5 — Первый запуск и проверка

### 5.1. Сборка и запуск контейнеров

**Что делает:** собирает образ Python-приложения и запускает все 3 контейнера.
**Зачем:** это момент, когда CRM «оживает».

```bash
cd /opt/crm && docker compose up --build -d
```

Разбор:

- `docker compose up` — «запусти всё по docker-compose.yml»;
- `--build` — «перед запуском собери образ заново» (нужно в первый раз);
- `-d` — «запусти в фоне» (чтобы можно было закрыть терминал).

Первый запуск длится **3–10 минут** (скачиваются образы Python и Postgres).
Жди, пока приглашение `root@...` вернётся.

**Ожидаемый результат:** в конце строки вида:

```
[+] Running 4/4
 ✔ Network crm_default   Created
 ✔ Container crm_db      Started
 ✔ Container crm_app     Started
 ✔ Container crm_nginx   Started
```

### 5.2. Проверка: контейнеры живы?

```bash
docker compose ps
```

**Ожидаемый результат:** три контейнера в статусе `Up` / `running`:

```
NAME        STATUS
crm_app     Up ...
crm_db      Up (healthy)
crm_nginx   Up ...
```

Если какой-то контейнер `Exited` или постоянно `Restarting` — смотри логи:

```bash
docker compose logs --tail=50 app
```

```bash
docker compose logs --tail=20 db
```

Чаще всего в логах `app` будет понятная ошибка (например, неверный пароль
базы — сверь `POSTGRES_PASSWORD` и `DATABASE_URL` в `.env`).

### 5.3. Миграции и демо-данные

**Что делает команда 1:** создаёт таблицы в базе (users, leads, ...).
**Зачем:** без таблиц сайту некуда сохранять данные.

```bash
cd /opt/crm && docker compose exec app flask db upgrade
```

**Ожидаемый результат:** строки вида `INFO [alembic...] Running upgrade ...`.

> Если команда ответила `Error: Can't locate revision` или ругань на
> `migrations` — значит папка миграций ещё не инициализирована.
> Выполни один раз (только в первый раз!):
> `docker compose exec app flask db init` — потом `stamp`/`migrate`:
> `docker compose exec app flask db migrate -m "init"`,
> затем снова `flask db upgrade`.

**Что делает команда 2:** создаёт демо-пользователя и 7 лидов.
**Зачем:** чтобы сразу увидеть заполненный канбан, а не пустой экран.

```bash
docker compose exec app python -m app.seed
```

**Ожидаемый результат:**

```
[seed] создан пользователь admin@example.com / admin123
[seed] создано 7 демо-лидов и 2 компании
```

При повторном запуске напишет «уже существует, пропускаю» — это нормально.

### 5.4. Открываем сайт в браузере (дома!)

Дальше — на **домашнем** компьютере. Открой браузер и введи:

```
http://ТВОЙ_IP_СЕРВЕРА
```

Например: `http://185.123.45.67`

**Что должно появиться:** страница входа Detroid CRM
(фиолетовая шапка, форма логина).

Введи демо-доступ:

- Email: `admin@example.com`
- Пароль: `admin123`

Нажми «Войти».

**Успех:** открылась Главная с карточками статистики и таблицей лидов.
Слева в меню нажми «Лиды (канбан)» — увидишь 5 колонок с карточками.
Попробуй перетащить карточку мышкой в другую колонку — стадия сохранится.

### 5.5. Возможные ошибки шага 5

| Симптом | Причина | Решение |
|---|---|---|
| Браузер: «Не удаётся подключиться» | Контейнеры не запущены / закрыт порт 80 | На сервере: `docker compose ps` (все Up?), `ufw status` (80 ALLOW?), `curl -I http://localhost` должен ответить `200 OK` |
| `502 Bad Gateway` от nginx | Flask упал или ещё стартует | Подожди 30 сек и обнови; смотри `docker compose logs --tail=50 app` |
| Страница входа зацикливается | Куки/кеш, неверный SECRET_KEY | Открой в режиме инкогнито; проверь `.env` |
| `FATAL: password authentication failed` в логах | Пароли в `.env` не совпадают | Сверь `POSTGRES_PASSWORD` и пароль внутри `DATABASE_URL`, затем `docker compose up -d --force-recreate` |
| `port 80 already in use` | На сервере уже стоит свой nginx/apache хостинга | Останови его: `systemctl stop nginx apache2 2>/dev/null; systemctl disable nginx apache2 2>/dev/null`, затем `docker compose up -d` |

## ШАГ 6 — HTTPS (замочек в браузере)

### Вариант А — автоматически скриптом (рекомендуется)

**Если у тебя есть домен**, указывающий на сервер (A-запись), — проще всего
выпустить свежий бесплатный сертификат Let's Encrypt одной командой.
Скрипт сам проверит DNS, выпустит сертификат, включит HTTPS в Nginx
и настроит автообновление.

На сервере выполни (подставь свой домен и email):

```bash
curl -fsSL -o /tmp/enable_https.sh https://raw.githubusercontent.com/Roses1s/detroid/arena/01a0c8d0-detroid/scripts/enable_https.sh && sudo bash /tmp/enable_https.sh ТВОЙ_ДОМЕН твоя@почта.ru
```

**Ожидаемый результат** в конце:

```
═══════════════════════════════════════════════════
 HTTPS включён ✅  Открой дома: https://ТВОЙ_ДОМЕН
 В адресной строке должен быть замочек 🔒
═══════════════════════════════════════════════════
```

Если скрипт остановился на проверке DNS — значит A-запись ещё не настроена
или не обновилась: создай её у регистратора домена и повтори через 5–30 минут.

**Если сертификат у тебя уже есть файлами** — загрузи их и запусти скрипт
в режиме `--existing` (он пропустит выпуск, а конфиг настроит сам):

```bash
# Выполнить ДОМА (замени пути, IP и домен):
scp /путь/к/fullchain.pem root@IP:/opt/crm/nginx/ssl/fullchain.pem
scp /путь/к/privkey.pem root@IP:/opt/crm/nginx/ssl/privkey.pem
# Выполнить НА СЕРВЕРЕ:
curl -fsSL -o /tmp/enable_https.sh https://raw.githubusercontent.com/Roses1s/detroid/arena/01a0c8d0-detroid/scripts/enable_https.sh && sudo bash /tmp/enable_https.sh ТВОЙ_ДОМЕН --existing
```

### Вариант Б — вручную (запасной)

Нужно положить сертификат в `nginx/ssl/` и включить HTTPS-блок в конфиге.

### 6.1. Положи файлы сертификата

Нужны два файла от твоего сертификата:

- `fullchain.pem` — сам сертификат (+ цепочка)
- `privkey.pem` — приватный ключ

Скопируй их на сервер (выполни ДОМА, замени IP и пути):

```bash
scp /путь/к/fullchain.pem root@185.123.45.67:/opt/crm/nginx/ssl/fullchain.pem
scp /путь/к/privkey.pem root@185.123.45.67:/opt/crm/nginx/ssl/privkey.pem
```

Если сертификат выпускался через панель spaceweb — скачай файлы из панели
и загрузи так же. Если использовался certbot прямо на сервере:

```bash
cp /etc/letsencrypt/live/ТВОЙ_ДОМЕН/fullchain.pem /opt/crm/nginx/ssl/fullchain.pem
cp /etc/letsencrypt/live/ТВОЙ_ДОМЕН/privkey.pem /opt/crm/nginx/ssl/privkey.pem
```

Проверь на сервере:

```bash
ls -la /opt/crm/nginx/ssl/
```

**Ожидаемый результат:** два файла `fullchain.pem` и `privkey.pem`.

### 6.2. Включи HTTPS в конфиге Nginx

На сервере открой конфиг:

```bash
nano /opt/crm/nginx/nginx.conf
```

Найди блок `HTTPS (включается после получения сертификата)` —
он закомментирован (`#` в начале строк). Удали символы `#` в начале
строк этого блока, укажи свой домен в `server_name`.
И раскомментируй редирект с HTTP на HTTPS в первом блоке
(строки с `return 301 https://...`).

Сохрани (`Ctrl+O`, Enter, `Ctrl+X`) и перезапусти nginx:

```bash
cd /opt/crm && docker compose restart nginx && docker compose ps
```

**Ожидаемый результат:** `crm_nginx` в статусе Up.

### 6.3. Проверка HTTPS

Дома открой:

```
https://ТВОЙ_ДОМЕН
```

**Ожидаемый результат:** сайт открылся, в адресной строке замочек,
браузер не ругается на сертификат.

Если будешь выпускать новый сертификат через Let's Encrypt прямо на сервере:

```bash
apt-get install -y certbot
certbot certonly --standalone -d ТВОЙ_ДОМЕН --agree-tos -m твоя@почта.ru
```

Потом скопируй файлы как в 6.1. Обновление — `certbot renew` (поставь в cron).

2. На сервере: `cd /opt/crm && sudo bash scripts/deploy.sh`.
3. Скрипт сам сделает `git pull`, пересоберёт образ, перезапустит и применит миграции.
4. Открой сайт и проверь.
